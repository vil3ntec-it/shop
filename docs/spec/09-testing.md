## ۹. آزمایش، کارایی و پایداری

### ۹.۱ سخت‌افزار و داده مرجع

| مورد | مشخصات |
|---|---|
| گوشی مرجع ضعیف | اندروید ۱۰ یا ۱۱، ۲ تا ۳ گیگابایت رم، کلاس Galaxy A0x یا itel یا Infinix ارزان |
| گوشی مرجع متوسط | اندروید ۱۳ یا ۱۴، ۴ گیگابایت رم، کلاس Galaxy A1x |
| کامپیوتر مرجع | ویندوز ۱۰ ۶۴ بیتی، Celeron یا i3 نسل ۴ تا ۶، ۴ گیگابایت رم، دیسک HDD |
| داده مرجع | ۲۰٬۰۰۰ کالا، ۳۰۰٬۰۰۰ ردیف فروش، ۵٬۰۰۰ مشتری، ۲٬۰۰۰ قرض‌دار فعال، ۵۰۰ تأمین‌کننده، ۱۰٬۰۰۰ عکس |
| شبکه مرجع | «3G ضعیف» (۴۰۰kbps، تأخیر ۴۰۰ms)، 2G (۵۰kbps، تأخیر ۸۰۰ms، ۵٪ از دست رفتن بسته)، و قطع کامل. برای امتیاز Lighthouse از throttling استاندارد موبایل خود Lighthouse استفاده شود |

داده مرجع با یک تولیدکننده قطعی (seed ثابت) ساخته می‌شود و در CI استفاده می‌شود. داده واقعی مشتری هرگز در ریپو قرار نمی‌گیرد.

### ۹.۲ بودجه‌های کارایی (p95 روی سخت‌افزار مرجع)

| عملیات | کامپیوتر | گوشی متوسط | گوشی ضعیف |
|---|---|---|---|
| اسکن تا ردیف فاکتور | ≤ ۱۰۰ms | ≤ ۱۵۰ms | ≤ ۲۵۰ms |
| جست‌وجوی کالا (هر حرف) | ≤ ۱۵۰ms | ≤ ۲۰۰ms | ≤ ۳۵۰ms |
| پایان فروش تا فرمان چاپ | ≤ ۵۰۰ms | ≤ ۷۰۰ms | ≤ ۱۲۰۰ms |
| باز شدن هر صفحه | ≤ ۳۰۰ms | ≤ ۴۰۰ms | ≤ ۸۰۰ms |
| شروع سرد برنامه | از خط پایه F0-26 تعیین شود (پیشنهاد ≤ ۶s روی HDD، با AppCDS) | ≤ ۲٫۵s | ≤ ۵s |
| گزارش ماه (۳۰۰ هزار ردیف) | ≤ ۲s در پس‌زمینه | ≤ ۳s | ≤ ۶s |
| حافظه در حال کار | ≤ ۵۰۰MB | ≤ ۳۰۰MB | ≤ ۲۰۰MB |

قاعده فعلی RULES («هر صفحه زیر ۱۰۰ میلی‌ثانیه با ۱۰۰۰ کالا») حفظ می‌شود. این جدول آن را تا داده مرجع بزرگ گسترش می‌دهد. **ویترین:** هدف‌های بخش ۳.۱۰.

**چه کسی اندازه می‌گیرد:**
- ایجنت به سخت‌افزار مرجع دسترسی ندارد. پس ابزار سنجش `bench` را می‌سازد (F0-26).
- صاحب محصول آن را روی دستگاه‌های مرجع اجرا می‌کند و خروجی را در PR می‌گذارد.
- CI روی ماشین‌های خودش فقط **افت نسبی** را بررسی می‌کند: هر افت بیش از ۱۰٪ نسبت به خط پایه، PR را رد می‌کند.

### ۹.۳ انواع آزمون (همه در CI)

1. **آزمون واحد موتورها** در `core/commonTest`، روی JVM و در صورت امکان JS.
2. **آزمون‌های مرجع مشترک** (`core/test-vectors/*.json`) روی Kotlin و JS. هر قاعده مالی حداقل ۲۰ مورد مرزی دارد: گردکردن، تخفیف، برگشت جزئی، شیفت شبانه، تبدیل واحد، ارقام فارسی و سال کبیسه.
3. **آزمون ویژگی‌محور** برای پول: «جمع تخصیص تخفیف = تخفیف کل» و «برگشت کامل = صفر شدن اثر» روی هزاران ورودی تصادفی.
4. **آزمون همگام‌سازی آشوب:**
   - op تکراری، خارج از ترتیب، تأخیر و قطع وسط بسته.
   - دو، سه و پنج دستگاه.
   - ۳۰ روز آفلاین (S26).
   - رقابت روی آخرین واحد (S27).
   - HLC (S28).
5. **آزمون قطع برق:**
   - حلقه ذخیره و `kill -9` (یا `taskkill /F` در ویندوز) در لحظه تصادفی، ۱۰۰ بار برای هر پلتفرم (S10).
   - در کامپیوتر، روی `windows-latest` در CI.
   - قطع برق واقعی در CI ممکن نیست. پیش از خروج فاز ۱ یک بار با `system_reset` در QEMU، یا دستی روی کامپیوتر مرجع.
   - پشتیبان SQLite هم در همین آزمون بررسی شود: پشتیبانی که وسط نوشتن گرفته شده، باید باز شود و سالم باشد.
6. **آزمون رابط کاربری:**
   - Compose UI test برای سناریوهای ⌨ (فقط رویداد کیبورد).
   - Playwright برای وب و ویترین، با محدودسازی شبکه.
   - اسکرین‌شات‌های `desktop-shots` برای همه صفحه‌ها در حالت روشن، تاریک و لمسی.
7. **آزمون دسترس‌پذیری:**
   - axe برای وب و ویترین (`test:web-ui` در CI).
   - کنتراست توکن‌ها.
   - برچسب‌های TalkBack در مسیرهای اصلی.
8. **آزمون سرور:**
   - مجموعه فعلی (حدود ۷۸۰ آزمون) روی PostgreSQL و PGlite.
   - آزمون‌های جدید برای سفارش، پرداخت با sandbox و وب‌هوک جعلی، اعلان و ویترین.
9. **آزمون بار (فقط روی PostgreSQL واقعی):**
   - ۲۰۰ فروشگاه × ۵ دستگاه، همگام‌سازی هم‌زمان پس از «قطع سراسری».
   - ۵۰ سفارش در دقیقه در ویترین.
   - p95 API ≤ ۳۰۰ms و بدون خطا.
   - سقف PGlite (تک‌اتصالی) جدا اندازه‌گیری و ثبت شود تا تصمیم D-01 با عدد گرفته شود.
10. **آزمون مهاجرت:**
    - روی کپی داده‌های واقعی، با رضایت مالک و داخل محیط امن.
    - گزارش تطبیق (بخش ۸، فاز ۱).
11. **آزمون نصب و به‌روزرسانی:**
    - نصب تازه.
    - به‌روزرسانی از نسخه قبلی با داده واقعی.
    - برگشت در صورت شکست.
    - امضای APK و `SHA256SUMS.sig`.

### ۹.۴ قواعد CI

- هیچ آزمونی نباید «بی‌صدا قبول» شود (F0-17). نبودن ابزار = شکست.
- آزمون‌های کامپیوتر روی `windows-latest` هم اجرا شوند، نه فقط نصب‌کننده.
- آزمون‌های کندِ آشوب و قطع برق می‌توانند شبانه اجرا شوند، ولی پیش از ادغام فاز اجباری‌اند.
- در هر PR، گزارش کوتاه کارایی (مقایسه با خط پایه) کامنت شود.

### ۹.۵ پایداری در محیط واقعی

- **پشتیبان:** OPS-02.
- **بازیابی:**
  - بازیابی آزموده هر ماه، به‌صورت خودکار روی داده مرجع.
  - «بازیابی تا آخرین پشتیبان و سپس اعمال op های صف» آزمون دارد.
- **سلامت دستگاه:** هشدار فضای کم دیسک و باتری کم.
- **ساعت دستگاه:** ساعت غلط می‌تواند ادغام را خراب کند. محافظت در بخش ۳.۸.۱ بند ۸ آمده و با سناریوی S28b آزموده می‌شود. ساعت عقب‌افتاده هشدار قرمز دارد.
