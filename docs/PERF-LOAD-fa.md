# آزمونِ بار (PERF-02) و فشارِ منابع (PERF-04)

ابزار و نتیجهٔ نخستین اجرای محلی — ۱۴۰۵/۰۸/۱۱ (۲۰۲۶-۱۱-۰۲)، نسخهٔ 2.14.5.

> ⚠️ **این عددها ظرفیتِ تولید نیستند.** یک ماشینِ مجازیِ مشترکِ ۴ هسته‌ای بود که بارساز، سرور و
> PostgreSQL را با هم و کنارِ کارهای دیگر (Gradle و آزمون‌های دیگر) اجرا می‌کرد. سخت‌افزارِ مرجع،
> شبکهٔ واقعی، تنظیمِ PostgreSQL ِ تولید و مقیاسِ هدفِ §۹.۳ (۲۰۰ دکان × ۵ دستگاه) سنجیده نشده‌اند.
> طبقِ §۱۵.۹ بندِ ۱ و §۲۹.۶ بندِ ۲ هیچ عددی این‌جا «ظرفیتِ تضمین‌شده» نیست.

## ابزار

| پرونده | کار |

| `server/scripts/load-test-server.mjs` | سرورِ آزمون در **فرآیندِ جدا**: همان `createApp` با keepAlive/headersTimeout و کارگرهای پس‌زمینهٔ `index.js`، کاشتنِ داده، و پاسخ به «حافظه/استخر/حلقهٔ رویداد/قفل‌ها چطور است؟» از راهِ IPC |

بی هیچ وابستگیِ تازه: `fetch` ِ خودِ Node، `node:child_process`، `perf_hooks`. دادهٔ ساختگی از همان

### اجرا

```bash
cd server
#  ⛔ پایگاه پاک می‌شود: فقط pglite:… یا پایگاهی که نامش test یا bench دارد
DB=postgres://shop:shoppass@127.0.0.1:5432/shop_load_bench
node scripts/load-test.mjs --db $DB --profile load,peak,burst --json load.json
node scripts/load-test.mjs --db $DB --profile soak --soak 600          # ثانیه
node scripts/load-test.mjs --db $DB --profile overload                 # PERF-04
node scripts/load-test.mjs --profile smoke --no-budget                 # PGlite در حافظه، چند ثانیه
#  گزینه‌ها: --rate 40 (درخواست در ثانیهٔ پایه) --shops 20 --devices 3 --scale 0.1 --small-scale 0.005
#            --history <op> --timeout 10000 --warmup 5 --max-inflight 512 --seed … --quiet
```

کدِ خروج: `0` همهٔ بودجه‌ها سبز؛ `1` بودجه‌ای رد شد؛ `3` بارساز خودش اشباع شد (بیش از ۱٪ درخواست جا افتاد) و
عددِ آن اجرا معتبر نیست؛ `2` ورودیِ نادرست. `--no-budget` فقط می‌سنجد.

### مدلِ بار

- **بارِ باز** (نرخِ رسیدنِ ثابت، نه N کاربرِ منتظرِ پاسخ): کندیِ سرور جلوی رسیدنِ درخواستِ بعدی را نمی‌گیرد و
  p99 پنهان نمی‌شود. سقفِ درخواستِ باز `--max-inflight` (۵۱۲)؛ بیش از آن «جاافتاده» شمرده می‌شود.
- زمانِ هر درخواست از فرستادن تا آخرین بایتِ پاسخ؛ مهلتِ کلاینت ۱۰ ثانیه (`timeout` ⇒ خطا). هر پاسخِ بیرون از
  ۲xx، مهلت و اتصالِ بریده خطاست.
- **داده:** ۲۰ دکان؛ دکانِ ۰ با مقیاسِ ۰٫۰۵ ِ دادهٔ مرجع (۱٬۰۰۰ کالا، ۱۰٬۰۰۰ فاکتور، ۱۵٬۰۰۰ قلم)، ۱۹ دکانِ
  کوچک با ۰٫۰۰۳ (۶۰ کالا)؛ روی هم ۶۳٬۸۴۱ ردیفِ دفتر، همهٔ کالاها در ویترین. پیش از بار: پلِ v1⇒v3 برای همهٔ
  دفتر (جدا سنجیده شد، پایین)، ۱۰٬۰۲۶ op ِ تاریخچهٔ v3، هر دستگاه تا سرِ دفتر، ۱۶ شمارهٔ تأییدشده در هر یک از
  ۴ ویترینِ سفارش‌گیر (سقفِ RSK-07: ۱۰ سفارش در ساعت برای هر شماره) و ۵ ثانیه گرم‌کردن — هیچ‌کدام ثبت نمی‌شوند.
- **ورود** با هزینهٔ scrypt ِ تولید (`PASSWORD_SCRYPT_P=5`)، نه p=1 ِ آزمون‌ها. سقف‌های نرخ (به‌ازای IP و حساب)
  باز شده‌اند چون همهٔ بار از یک ماشین می‌آید؛ خودِ سقف‌ها آزمون‌های جدای خودشان را دارند.

| برچسب | درخواست | وزن |
|---|---|---|
| `store.home` / `store.products` / `store.search` / `store.product` | `GET /api/store/:slug`، صفحهٔ اولِ کالاها، جست‌وجو (`?q=`)، صفحهٔ کالا — نیمی دکانِ بزرگ، نیمی تصادفی | ۶ / ۱۶ / ۱۲ / ۱۴ |
| `store.checkout` | `POST /api/store/:slug/checkout` (تحویل در دکان، ۱ تا ۳ قلم، کلیدِ یکتایی، بلیتِ شمارهٔ تأییدشده) | ۴ |
| `store.track` | `GET /api/store/:slug/orders/:token` برای سفارش‌های همین اجرا | ۶ |
| `sync3.push` / `sync3.pushLarge` | `POST /api/sync/v3/push`: ۱ تا ۲ فروش (۴ تا ۲۰ op: سند، قلم، حرکتِ موجودی، تراکنش در یک tx)؛ ۱۰٪ صفِ برگشت از آفلاین (۴۵ تا ۶۰ فروش، سقفِ ۵۰۰ op) | ۱۲ |
| `sync3.pull` | `GET /api/sync/v3/pull` با cursor ِ همان دستگاه (هر دستگاه نشستِ خودش؛ push/pull ِ هم‌زمانِ یک دستگاه نیست) | ۱۲ |
| `desk.list` / `desk.summary` | `GET /api/shop/orders?tab=…&limit=50` و `/summary` ِ صاحبِ دکان | ۹ / ۳ |
| `auth.login` / `auth.refresh` | `POST /api/auth/login` و `/refresh` (نشستِ چرخان) | ۲ / ۴ |

| نمایه | شکل |
|---|---|
| `load` | ۶۰ ثانیه، `rate` (۴۰/s) |
| `peak` | ۶۰ ثانیه، ۲٫۵ × `rate` (۱۰۰/s) |
| `burst` | ۵ ثانیه ۴۰/s ⇐ ۵ ثانیه ۲۰۰/s با آمیزهٔ پرهمگام‌سازی **و** هم‌زمان همهٔ ۶۰ دستگاه یک صفِ برگشت از آفلاین می‌فرستند و pull می‌کنند («قطعِ سراسری»، §۹.۳ بندِ ۹، §۱۵.۹ بندِ ۲) ⇐ ۱۰ ثانیه ۴۰/s |
| `soak` | `--soak` ثانیه (۳۰۰) با ۴۰/s؛ هر ۵ ثانیه نمونهٔ سرور، هر ۶۰ ثانیه پس از GC |
| `overload` | PERF-04: سرورِ جدا با `PG_POOL_MAX=2` و `PG_CONNECT_TIMEOUT_MS=1000`، ۱۵ ثانیه ۴ × `rate`؛ سپس بازگشت |
| `smoke` | ۳ ثانیه — فقط برای CI و دودآزمایی |

سرور در هر نمونه: RSS، heap (و heap پس از GC با `--expose-gc`)، CPU ِ فرآیند، بیشینهٔ تأخیرِ حلقهٔ رویداد،
استخرِ `pg` (کل/بیکار/**صفِ انتظار**) و روی PostgreSQL از استخرِ جدای یک‌اتصالی: اتصال‌های فعال، **پشتِ قفل**
و idle-in-transaction (`pg_stat_activity`)، و دروازهٔ push ِ v3 (منتظرِ بی اتصال و push ِ در کار).

## بودجه‌ها — پیش از اجرا ثابت (§۲۹.۶ بندِ ۵)

در `BUDGET` ِ همان ابزار؛ عوض کردنشان پس از اجرا یعنی سبز کردنِ شکست.

| بودجه | مقدار | منبع |
|---|---|---|
| p95 ِ هر مسیر | ≤ ۳۰۰ms | §۹.۳ بندِ ۹ «p95 API ≤ ۳۰۰ms و بدون خطا» |
| خطا | ۰ (هر پاسخِ بیرون از ۲xx، مهلت، اتصالِ بریده) | همان بند |
| soak: کند شدنِ تدریجی | p95 ِ دقیقهٔ آخر ≤ ۱٫۵ × دقیقهٔ اول + ۲۰ms | PERF-04 (عدد را همین ابزار گذاشت؛ spec عدد ندارد) |
| soak/overload: نشتِ حافظه | heap پس از GC در پایان ≤ آغاز + بیشینهٔ (۳۲MB، ۲۵٪) | PERF-04 (همان) |
| overload | فقط ۲xx/۴۲۹/۵۰۳ (نه ۵۰۰، نه مهلت، نه اتصالِ بریده)؛ ≤ ۱۰ ثانیه پس از بار، درخواستِ عادی بی خطا و زیرِ ۳۰۰ms | §۱۵.۹ بندِ ۴، §۲۹.۶ بندِ ۷ |

### burst — «قطعِ سراسری»: ۶۰ دستگاه با صفِ پر + ۲۰۰/s (دو اجرا)

| | اجرای ۱ | اجرای ۲ |
|---|---|---|
| درخواست / خطا / جاافتاده | ۹۳۰ / **۴۹۷** / ۴۳۴ | ۹۴۳ / **۵۱۴** / ۴۰۲ |
| خطاها | مهلتِ ۱۰ ثانیهٔ کلاینت (+ ۶ ۵۰۳ ِ `db_busy`) | مهلتِ ۱۰ ثانیه |
| صفِ انتظارِ استخر (بیشینه) | ۵۶۴ | ۷۶۱ (اتصالِ پشتِ قفل ≤ **۶ از ۱۰**) |
| p50 / p95 ِ ویترین (`store.products`) | 10000 / 10004 ms | 10000 / 10002 ms |
| `sync3.pushLarge` p50 / p95 | 10001 / 10004 ms | 10003 / 10010 ms |
| پس از burst | صفِ استخر در ~۲ ثانیه صفر؛ heap پس از GC ۲۸٫۱ ⇐ ۲۹٫۷MB | heap ۲۸٫۳ ⇐ ۳۰MB |

بودجهٔ «p95 ≤ ۳۰۰ms و بی خطا» ِ §۹.۳ بندِ ۹ برای burst **با فاصلهٔ زیاد رد شد** — آن هم با ۶۰ دستگاه، نه ۱٬۰۰۰ ِ هدف.
سرور نیفتاد، حافظه برگشت و پس از burst دوباره پاسخ داد؛ ولی در خودِ burst بیشترِ درخواست‌های ویترین و میزِ سفارش
۱۰ ثانیه منتظرِ استخر ماندند. ریشه پایین (یافتهٔ ۲).

  اتصالِ پشتِ قفل ۰ — استخر تمام نشد. بیشینهٔ تأخیرِ حلقهٔ رویداد ۱۷۲ms (یک نمونه، ثانیهٔ ۲۵۰).
- **بودجهٔ کند شدن رد شد:** p95 ِ دقیقهٔ آخر ۱۴۵ms > سقفِ ۹۱٫۹ms؛ ورود (p95 ‏۳۱۰ms) و push ِ بزرگ (p95 ‏۱٫۷s) هم مثلِ
  load. هم‌زمان بارِ ماشین از ۱٫۰ به ۳٫۳ رسید (کارهای دیگر، از جمله Gradle) و p50 ِ همه هم ۲۸٪ بالا رفت؛ از این
  اجرا نمی‌شود گفت سهمِ رشدِ داده (opهای تازهٔ v3) چقدر است. ابزار حالا p50/p95 ِ هر مسیر را در هر پنجره هم
  می‌نویسد (`driftBy`) تا اجرای بعدی این دو را جدا کند.
- soak ِ نخست (اجرای ۲) کنار گذاشته شد: پنجرهٔ آخرش بر پایهٔ **پایانِ** درخواست بود و فقط کُندهای جامانده پس از
  پایانِ بار را داشت (۱٬۲۳۵ms ِ ساختگی). ابزار درست شد (پنجره بر پایهٔ آغازِ درخواست، پنجرهٔ نیمه‌کاره کنار) و
  عددهای بالا از اجرای دوباره‌اند.

### overload (PERF-04) — استخرِ ۲ اتصال، مهلتِ اتصالِ ۱ ثانیه، ۱۶۰/s خواسته (بارِ ماشین ۵٫۴ ⇐ ۵٫۹)

  پایانی همان ~۱ ثانیه ماند و در اجرای میانی (بارِ ماشین بیشتر) تا ۳٫۳ ثانیه رفت. push کارِ پس‌زمینهٔ دستگاه است و
  ویترین کارِ مشتری؛ این جابه‌جایی عمدی است (`SYNC_V3_PUSH_SLOTS`).
- **burst دیگر همه‌چیز را نمی‌خواباند**: پیش ۴۷۲ از ۹۴۴ مهلت (و ۴۱۰ درخواست اصلاً فرستاده نشد، چون ۵۱۲ درخواستِ
  باز پر بود)؛ پس ۴۰ از ۱٬۲۵۲، همه push ِ بزرگ و همه ۵۰۳ ِ `db_busy` با `Retry-After: 2` (هیچ چیزی اعمال نشده و
  برنامه همان دسته را دوباره می‌فرستد). ویترین و میز ۱ ثانیه‌ای ماندند، نه ۱۰ ثانیه — هنوز بیرون از بودجه.
- **چرا انتظارِ ۸ ثانیه، نه ۱۵:** در اجرای میانی ۴۲ push در ۱۰ ثانیه از سوی کلاینت رها شدند و ۵۰۳ ِ دروازه (پس از
  ۱۵ ثانیه) وقتی رسید که کلاینت رفته بود (۱۵ خطِ `db_busy` در لاگ، بی گیرنده). سقفِ کمتر از مهلتِ معمولِ کلاینت یعنی
  سرور پیش از رفتنِ او پس می‌زند و کارِ بی‌گیرنده نمی‌کند.

## یافته‌ها

### درست شد (همین شاخه، با آزمون)

1. **استخرِ پر ⇒ ۵۰۰ ِ «خطای داخلیِ سرور».** درخواستی که تا `PG_CONNECT_TIMEOUT_MS` اتصال نمی‌گرفت پیامِ خامِ
   pg-pool (`timeout exceeded when trying to connect`) را به ۵۰۰ می‌برد. حالا `middleware/errors.js` آن را ۵۰۳ ِ
   `db_busy` با `Retry-After: 2` و پیامِ «سرور الان شلوغ است…» می‌کند (§۱۵.۹ بندِ ۴: خطای قابلِ فهم و retry ِ
   محدود) و برای همین یک کد فقط یک خط لاگ می‌نویسد، بی stack — در burst صدها بار در ثانیه می‌رسید.
   `test/db-pool-busy.test.js` (PostgreSQL محلی ۲/۲؛ PGlite ۱ + ۱ رد شده چون استخر ندارد). ۵۰۳ ِ burst ِ اجرای ۱
   همین کد است.
2. **push ِ منتظرِ همان دکان اتصال نگه می‌داشت (یافتهٔ ۲ ِ پیشین) — `claude/sync-pool-backpressure`.** `lib/sync-v3-gate.js`:
   هر تراکنشِ قفل‌دارِ v3 (push، پلِ v1⇒v3، بستنِ تعارض) اول در صفِ همان فرآیند و همان کلیدِ قفل نوبت می‌گیرد، و
   push جایی از سقفِ هم‌زمان (`SYNC_V3_PUSH_SLOTS`، پیش‌فرض نیمِ استخر)؛ **بعد** اتصال، و درونِ تراکنش همان
   `pg_advisory_xact_lock` ِ پیشین. همان تراکنش و همان قفل ⇒ همان ترتیب، اتمی بودنِ واحدها، تکراری‌ها و ردها؛ اندازهٔ
   دسته‌ها دست نخورد (هیچ واحدِ tx شکسته نشد). **میانِ دو نمونهٔ سرور** روی یک پایگاه انتظار هنوز پشتِ قفلِ پایگاه و
   با اتصال است (یک اتصال برای هر دکان در هر نمونه، نه یکی برای هر دستگاه). PGlite: خاموش (یک اتصال، `db.tx` خودش پشتِ
   سرِ هم می‌گذارد). آزمون: `test/sync-v3-gate.test.js` (PostgreSQL محلی ۴/۴، PGlite ۱ + ۳ رد شده):
   ۷ دستهٔ هم‌زمانِ یک دکان (۶ دستگاه + شاگرد، دو دور) ⇒ همان پاسخِ هر op، همان دفتر به همان ترتیب، همان ردیف‌ها و
   تعارض‌ها که اجرای پشتِ سرِ هم روی دکانِ دوم، و opهای هر push در دفتر پیوسته (بی دروازه و بی قفل همین آزمون سرخ
   می‌شود: «هر push یک بازه … ۷ !== ۱۵»)؛ ۵ push ِ منتظرِ یک دکان پشتِ قفلِ بیرونی ⇒ ۱ اتصال (پیش: ۵).
3. **پس‌زدنِ زود (بخشی از یافتهٔ ۳ ِ پیشین).** دروازه انتظار و صف را سقف می‌زند (`SYNC_V3_GATE_WAIT_MS` ‏۸ ثانیه،
   `SYNC_V3_GATE_QUEUE_MAX` ‏۲۰۰) و بیرون از آن ۵۰۳ ِ `db_busy` با `Retry-After` می‌دهد، پیش از گرفتنِ اتصال؛ برای بقیهٔ
   مسیرها `PG_POOL_MAX_WAITING` (پیش‌فرض ۰ = خاموش) صفِ pg-pool را سقف می‌زند و تازه‌وارد بی‌درنگ همان ۵۰۳ را می‌گیرد،
   نه پس از `PG_CONNECT_TIMEOUT_MS` (۱۰ ثانیه، همان مهلتِ انتظار برای اتصال که پیش‌تر هم بود). همان آزمون: انتظارِ بلند،
   صفِ پر، سقفِ push و صفِ استخرِ پر ⇒ ۵۰۳ + `Retry-After: 2`، ۰ × ۵۰۰، و همان دسته پس از آزاد شدن اعمال می‌شود.

### مانده (اندازه‌گرفته، درست نشده)

1. **ورود از بودجهٔ ۳۰۰ms بیرون است حتی در بارِ معمول** (p95 ‏۳۰۹ms، p50 ‏۲۳۲ms). خودِ scrypt ِ p=5 (SEC-AUTH-01)
   ~۲۰۰ms هزینه دارد و عمدی است. یکی باید عوض شود: بودجهٔ جدا برای ورود (پیشنهاد: ≤ ۵۰۰ms) یا هزینهٔ هش — تصمیمِ صاحبِ
   محصول، نه این ابزار.
2. *(بخشِ قفل درست شد — بالا، «درست شد» ۲؛ خودِ هزینهٔ push ِ بزرگ مانده)* **push ِ بزرگِ v3 (۲۰۰ تا ۵۰۰ op) ~۱ تا ۲ ثانیه یک اتصالِ استخر را نگه می‌دارد** (حدودِ ۲ms برای هر op در بارِ معمول؛
   `applyOne` برای هر op جدا). **و قفلِ حساب (`pg_advisory_xact_lock` در `lib/sync-v3.js`) درونِ تراکنش گرفته
   می‌شود**: دستگاهِ دومِ همان دکان اتصالش را در حالِ انتظار برای قفل نگه می‌دارد. در burst تا ۶ از ۱۰ اتصال پشتِ
   همین قفل بیکار بودند و ویترین ۱۰ ثانیه منتظرِ استخر ماند. پیشنهادها (هیچ‌کدام کوچک نیست): صفِ همان فرآیند برای
   هر حساب **پیش از** گرفتنِ اتصال (مثلِ `lib/account-lock.js`)، سقفِ push ِ هم‌زمان (bulkhead) تا خواندنِ ویترین
   همیشه اتصال داشته باشد، و ارزان‌تر کردنِ اعمالِ دسته‌ای (پلنِ پرس‌وجو و نمایه: PERF-03، شاخهٔ جدا).
3. *(برای push و، اگر روشن شود، صفِ استخر درست شد — بالا، «درست شد» ۳؛ مهلتِ سراسریِ درخواست و پیش‌فرضِ `PG_POOL_MAX_WAITING` مانده)*
   **سرور زیرِ فشار پس نمی‌زند (backpressure ندارد).** صفِ `pg-pool` در طول نامحدود است (فقط زمانِ هر انتظار
   سقف دارد)، درخواستِ HTTP مهلتِ سراسری ندارد و پذیرشِ تازه با صف بسته نمی‌شود؛ پس به‌جای ۵۰۳ ِ زود، همه کند
   می‌شوند (peak و burst). پیشنهاد: پذیرشِ کنترل‌شده (مثلاً صفِ استخر بالای سقف ⇒ ۵۰۳ ِ فوری) — تصمیمِ طراحی.
4. **پلِ v1⇒v3 برای دکانی که دفترش در v1 است ~۴۰۰ op/s است و درونِ نخستین pull ِ v3 اجرا می‌شود** (تا ۳ × ۱۰۰۰ op
   در هر درخواست، زیرِ قفلِ حساب). روی PGlite در اجرای دود ~۲۴۰ op/s بود و نخستین pull از ۱۰ ثانیه گذشت. دکانِ
   بزرگِ مرجع (~۶۰۰k ردیف) یعنی دقیقه‌ها پل در درخواست‌های pull. پیشنهاد: پل در پس‌زمینه یا با سقفِ زمانِ هر درخواست.
5. **ظرفیتِ این ماشین برای آمیزهٔ بالا میانِ ۴۰ و ۱۰۰ درخواست در ثانیه است**؛ CPU ِ فرآیندِ سرور در peak ~۲۳۰ تا ۳۰۰٪
   و PostgreSQL و بارساز روی همان ۴ هسته. عدد روی سخت‌افزارِ جدا (سرور/پایگاه/بارساز) باید دوباره گرفته شود.

## چه مانده تا PERF-02/PERF-04 کامل شوند

- اجرا روی سخت‌افزارِ مرجع/میزبانِ هدف، بارساز جدا از سرور، و با مقیاسِ §۹.۳ (۲۰۰ دکان × ۵ دستگاه، ۵۰ سفارش در دقیقه).
- اجرای جدای PGlite (همان ابزار: `--db pglite:<پوشه>`) و ثبتش کنارِ PostgreSQL (PERF-06).
- soak ِ بلند (ساعت‌ها، با رشدِ دیتاست) و I/O ِ دیسک و اندازهٔ پایگاه در طولِ زمان؛ CPU ِ PostgreSQL جدا.
- burst هنوز بیرون از بودجه است (ویترین p95 ~۱ ثانیه، ۴۰ × ۵۰۳ ِ push): ارزان‌تر کردنِ push ِ بزرگ (PERF-03)، تصمیمِ
  پیش‌فرضِ `PG_POOL_MAX_WAITING` (۰ = خاموش، تا مسیرهای پمپ و v1 بی آزمونِ بار ۵۰۳ ِ تازه نگیرند)، مهلتِ سراسریِ درخواست،
  و تصمیمِ بودجهٔ ورود؛ سپس دوباره همین نمایه‌ها. نمایهٔ `overload` پس از دروازه دوباره اجرا نشد.
- اجرای زمان‌بندی‌شده در CI (مثلاً کنارِ `perf.yml`) فقط برای **افتِ نسبی**، نه بودجهٔ مطلق.
