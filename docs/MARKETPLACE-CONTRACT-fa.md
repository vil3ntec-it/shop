# قراردادِ دادهٔ دکان ⇐ بازار (نسخهٔ ۱، ۱۴۰۵/۰۸/۰۸)

> پایه: تصمیم‌های صاحب محصول در `docs/spec/40-owner-decisions.md` (§۴۰.۱، §۴۰.۴، §۴۰.۵) و بخش‌های ۲۳، ۳۰، ۳۱ و ۳۲ِ سند.
> این فایل **طراحی** است؛ هیچ کدی با آن عوض نشده. هر جا «الان هست» آمده، از کدِ همین شاخه خوانده شده است (`server/`).
> اگر این فایل با سند تعارض داشت، سند مقدم است و تعارض باید به صاحب محصول گزارش شود.

## ۰. اصلِ قرارداد در یک جمله

**دکان صاحبِ داده است، سرور تنها مرجعِ عمومی است، بازار فقط ویترین است.**
برنامهٔ مدیریت داده را می‌سازد و به سرور می‌فرستد؛ سرور آن را می‌سنجد، «نمای عمومی» می‌سازد و فقط همین نما را به
بازار (برنامه و سایتِ خرید، و بعداً API و تبلیغات) می‌دهد. بازار هیچ‌وقت مستقیم به دستگاهِ دکان یا جدول‌های داخلی
(`sync_rows`، دفترِ موجودی، صندوق) دست نمی‌زند، و خطا یا شلوغیِ بازار نباید به صندوق و فروشِ حضوری برسد (§۴۰.۴).

سه لایه:

| لایه | صاحب | کجا | چه کسی می‌نویسد |
|---|---|---|---|
| ۱. دادهٔ عملیاتیِ دکان | دکان | دستگاه + `sync_rows` / `sync_v3_rows`، دفترِ موجودی | فقط برنامهٔ مدیریت (همگام‌سازی) |
| ۲. تنظیمِ انتشار | دکان | `storefronts`، `storefront_products`، `market_listings`، … | برنامهٔ مدیریت از راهِ `/api/shop/*` با مجوزِ کارمند |
| ۳. نمای عمومی (قرارداد) | سرور | پاسخ‌های `/api/store/*` و `/api/market/*` (و بعداً `/api/public/v1/*`) | فقط سرور، فقط‌خواندنی برای بازار |

قاعدهٔ طلایی: **هر فیلدی که در لایهٔ ۳ نیست، برای بازار وجود ندارد.** شناسهٔ داخلی، شمارهٔ مالک، ایمیل، مختصاتِ دقیقِ دکان،
مقدارِ دقیقِ موجودی (مگر دکان خواسته باشد) و قیمتِ خرید هرگز در نمای عمومی نمی‌آیند (همین حالا هم در `lib/market.js` رعایت می‌شود).

## ۱. موجودیت‌ها: دکان دقیقاً چه چیزی منتشر می‌کند

برای هر موجودیت: فیلدها، **مالک** (چه کسی حقِ تغییر دارد)، **تازگی** (چقدر کهنه مجاز است و چه نشان داده می‌شود)،
**احراز** (چه کسی می‌خواند/می‌نویسد) و **وضعیتِ امروز** (✅ هست، 🟡 نیمه، ❌ نیست).

### ۱.۱ دکان (پروفایلِ عمومی)

| فیلدِ عمومی | منبعِ امروز | وضعیت |
|---|---|---|
| `slug` (نشانیِ یکتا، ۳ تا ۳۲ حرفِ لاتین) | `storefronts.slug` (مهاجرت ۰۶۶) | ✅ |
| `title`, `tagline`, `notice`, `accent`, `contactPhone` | `storefronts` | ✅ |
| `category` (دستهٔ دکان از فهرستِ ثابت)، `area` (محله)، `geo` گردشده | `market_listings` (۱۱۴) + `CATEGORIES` در `lib/market.js` | ✅ |
| `listed` (خواستِ صاحب دکان برای آمدن در فهرستِ بازار)، `showDeals` | `market_listings.listed/show_deals` (۱۱۴، ۱۱۷) | ✅ |
| `fulfillment` (ارسال/تحویل در دکان)، `deliveryFeeMinor`، `minOrderMinor`، `currency` | `storefronts` | ✅ (ارز ثابتِ `AFN`) |
| `payment.methods` | ثابت `['cod']` در `profile()` ِ `lib/storefront.js` | 🟡 پرداختِ آنلاین منتظرِ D-08 |
| **لوگو و تصویرِ سرِ صفحه** | — | ❌ هیچ ستونی نیست |
| **شناسهٔ عمومیِ پایدارِ دکان** (جدا از `slug`) | `storefronts.public_id` (ULID، تغییرناپذیر) و `storefront_slug_redirects` (مهاجرت ۱۲۲)؛ `GET /api/store?id=` و ۳۰۸/۳۰۱ از نشانیِ کهنه | 🟡 پشتِ پرچمِ خاموشِ `market.public_id` (S3) |
| **امتیاز/نظرِ مشتری** | — | ❌ (فقط شکایت/گزارش در `trust_cases`) |
| **وضعیتِ اعتماد** (جریمهٔ فعال) | `trust_sanctions` (۱۰۱) با `suspend_storefront` | ✅ اثر می‌گذارد، ولی در نمای عمومی فیلدِ صریح ندارد |

- **مالک**: صاحب دکان/مدیر (`PUT /api/shop/storefront`، `PUT /api/shop/market`). مدیرِ سامانه فقط می‌تواند پنهان یا تعلیق کند (پرچمِ `market.directory` برای هر دکان، `trust_sanctions`)، نه محتوا را عوض کند.
- **تازگی**: پروفایل تا `config.market.eligibleCacheMs` در برشِ بازار کهنه می‌ماند؛ «روشن/فعال/listed» در هر درخواست زنده سنجیده می‌شود (`lib/market.js`، سرِ فایل).
- **احراز**: خواندن بی‌توکن؛ نوشتن فقط با نشستِ کارمندِ همان دکان و مجوز.
- **دروازه‌ها** (همه باید روشن باشند، وگرنه ۴۰۴ مثلِ نشانیِ ناموجود): پرچم‌های `shop.orders` و `shop.storefront` + کلیدهای اشتراکِ `online_orders` و `storefront` + `storefronts.enabled` + دکانِ فعال؛ برای فهرستِ بازار هم `market.directory` + `listed` + دست‌کم یک کالای منتشرشده.

### ۱.۲ وضعیتِ حضور و ساعتِ کاری (§۳۱)

| فیلدِ عمومی | منبع | وضعیت |
|---|---|---|
| `status.badge` = `open_online` / `open_unconfirmed` / `declared_until` / `closed` / `offline` | `presenceOf()` در `lib/storefront.js` | ✅ |
| `status.connection` = `confirmed` / `unconfirmed` / `lost` و `lastConfirmedAt` (زمانِ واقعی) | `MAX(sync_devices.last_seen_at)` | ✅ |
| `status.orderAcceptance` = `accepting` / `delayed` / `later` (جدا از حضور، §۳۱.۲ بندِ ۷) | همان | ✅ |
| `timezone`، `localTime`، `today`، `holiday`، ساعتِ هفتگی، روزهای تعطیل | `storefronts.weekly_hours/closed_dates/timezone` | ✅ |
| `declaredUntil` | `storefronts.declared_until` | ✅ |
| تاریخچهٔ اعلام‌ها با `event_id`، `actor_id`، `source_device_id`، `client_event_at`، `server_received_at` | `storefront_presence_events` (۰۶۶) | ✅ |

- **مالک**: صاحب دکان (`POST /api/shop/storefront/presence`). زمانِ سرور مرجع است.
- **تازگی**: «اتصال» از آخرین تماسِ همگام‌سازی است، نه ضربانِ جدا. آستانه‌ها `config.storefront.staleMs/offlineMs`.
- **کمبود**: 🟡 ضربانِ واقعی جدا از همگام‌سازی نیست؛ دستگاهی که باز است ولی چیزی برای همگام‌سازی ندارد ممکن است «تأییدنشده» دیده شود. 🟡 هر بار `MAX(last_seen_at)` از نو پرسیده می‌شود؛ برای صدها دکان در یک صفحهٔ بازار باید یک ستونِ آماده (مثلاً `storefronts.last_seen_at`) نگه داشته شود.

### ۱.۳ کالا (فهرستِ منتشرشده)

| فیلدِ عمومی | منبعِ امروز | وضعیت |
|---|---|---|
| `id` (شناسهٔ کالای خودِ دکان، ثابت) | `sync_rows.row_id` = `storefront_products.product_id` | ✅ |
| `name`, `unit`, `category` | `sync_rows.data` (v1) | 🟡 فقط v1 |
| `priceMinor` (قیمتِ آنلاین، وگرنه قیمتِ فروشِ دفتر) | `storefront_products.online_price_minor` یا `data.salePrice` | ✅ (سرور می‌گوید، عددِ مشتری خوانده نمی‌شود) |
| `maxQtyMilli` | `storefront_products.max_qty_milli` | ✅ |
| `description`, `specs`, `publishedAt` | `storefront_products` (۱۱۱) | ✅ |
| `photo` (دارد/ندارد) + نشانیِ `photo`/`thumb` | `product_photos` یا بانکِ تصاویر (`shop_product_images`) | ✅ |
| `stock` (نشانِ موجودی؛ بخشِ ۱.۴) | `catalog.publicStock()` | 🟡 پشتِ پرچمِ `shop.catalog` |
| **برند، بارکد، زیردسته، variant (اندازه/رنگ)، واحدِ فروش و ضریب** | در `catalog_products` (۰۸۲) هست | ❌ در نمای عمومی نیست |
| **دستهٔ سراسریِ کالا** (برای جست‌وجوی بازار در همهٔ دکان‌ها) | دستهٔ کالا متنِ آزادِ هر دکان است | ❌ |
| **پیوند به بانکِ مرکزیِ کالا** (`bank_product_id`، GTIN) برای «همین کالا در دکان‌های دیگر» | `shop_product_images.bank_product_id` | 🟡 هست ولی منتشر نمی‌شود |
| **نسخه/زمانِ تغییرِ کالا** (`updatedAt`, `etag`) | — | ❌ |

- **مالک**: نام، قیمت، واحد، فعال/غیرفعال را **فقط برنامهٔ مدیریت** (همگام‌سازی) می‌سازد؛ انتشار، قیمتِ آنلاین، توضیح و سقفِ تعداد با `PUT /api/shop/storefront/products/:productId`. مدیرِ سامانه فقط پنهان می‌کند (`trust_sanctions.kind = 'hide_listing'`).
- **قاعدهٔ «زنده»**: منتشرشده + حذف‌نشده + فعال + قیمت‌دار + بی جریمهٔ پنهان (`PRODUCT_FROM` و `LIVE_PRODUCT`). همین قاعده در فهرست، جست‌وجوی بازار و ثبتِ سفارش یکی است — باید یکی بماند.
- **تازگی**: نام/قیمت تا رسیدنِ همگام‌سازیِ بعدیِ دستگاه کهنه است؛ نمایهٔ جست‌وجوی بازار (`market_search`) با امضای کالاها فقط برای دکانِ تغییرکرده تازه می‌شود و هر نتیجه دوباره با دادهٔ زنده سنجیده می‌شود.
- **کمبودِ مهم** ❗: ویترین و بازار مستقیم از `sync_rows` ِ v1 می‌خوانند (`SHOP_ROWS` در `lib/storefront.js`)؛ `sync_v3_rows` آن‌جا هیچ اثری ندارد. کاتالوگِ واحد (`catalog_products`) هر دو منبع را می‌شناسد (`catalog_settings.sync_source`) ولی ویترین از آن نمی‌خواند. **با کوچِ دکان به همگام‌سازیِ v3، ویترین و بازارش خالی می‌شود.**

### ۱.۴ موجودی (§۳۲)

| فیلدِ عمومی | معنی | وضعیت |
|---|---|---|
| `stock.status` | «در قفسه» / «در انبار، آماده‌سازی لازم» / «تمام شده» / «در حال بررسی» / «قابلِ سفارش نیست» | ✅ وقتی `shop.catalog` روشن؛ وگرنه همیشه `unverified` |

| `stock.qty` | فقط اگر `catalog_settings.show_qty = 'exact'` | ✅ |
| `prepMinutes` | زمانِ آماده‌سازیِ اعلام‌شده | ✅ (`catalog_settings.prep_minutes`) |

- **مالک**: دفترِ موجودی (`stock_moves`، append-only، با `source_key` یکتا) فقط از دستگاه‌های دکان و کارمندِ مجاز.
- **تازگی**: `catalog_settings.stale_after_sec` (پیش‌فرض ۹۰۰ ثانیه)؛ کهنه ⇒ «در حال بررسی»، هرگز «موجود» (INV-02/14).
- **تعارضِ باز** ⚠️: تصمیمِ صاحبِ مخزن (۱۴۰۵/۰۷/۲۷، سرِ `lib/catalog.js`) می‌گوید سفارشِ آنلاین موجودی را **نه رزرو می‌کند نه کم**؛ ولی §۳۲.۲ بندِ ۲ رزروِ اتمی می‌خواهد تا دو مشتری قلمِ آخر را با هم نخرند. جدولِ `stock_reservations` ساخته شده ولی استفاده نمی‌شود. در بازارِ چنددکانیِ پرترافیک این تعارض جدی‌تر می‌شود و **باید صاحب محصول یک بار تصمیم بگیرد** (پیشنهاد در بخشِ ۳، کارِ M5).

### ۱.۱۰ هویتِ مشتری

✅ `store_customers` (۱۱۲) **سراسری** است (یکتا بر شماره، نه بر دکان) با نشست، نشانی‌ها و لغوِ نسلیِ نشست (`store_phone_revocations`) — همین برای بازارِ چنددکانی درست است.
🟡 ولی مسیرهای حساب زیرِ `/api/store/:slug/account` هستند؛ برنامهٔ خرید باید بتواند بی انتخابِ دکان وارد شود (`/api/market/account/*`).

## ۲. خلاصهٔ «هست / کم است»

**هست و قابلِ تکیه** (دوباره ساخته نشود): ویترینِ هر دکان، فهرست و جست‌وجوی بازار، حضور و ساعتِ کاری با رویداد،
ناحیه و زمان‌بندی، سفارش با کلیدِ یکتایی و قیمتِ سرور، پیگیری با توکن، حسابِ سراسریِ مشتری، OTP، outboxِ اعلان،
مهلتِ پذیرش، پیکِ دکان با کد/عکس/تسویه، گفت‌وگو، شکایت و جریمه، بانکِ تصاویر، دفترِ موجودیِ append-only.

**کمبودهای ساختاری** (اگر الان ساخته نشوند، بعداً دوباره‌کاری دارند):

1. ویترین فقط از `sync_rows` ِ v1 می‌خواند ⇒ با v3 می‌شکند.
2. «نمای عمومی» در کد پراکنده است (`productView`، `profile`، `publicOrder`، `cardOf`) و نسخه/طرحِ ثابت ندارد.
3. شناسهٔ عمومیِ پایدار برای دکان نیست (فقط `slug` ِ تغییرپذیر).
4. هیچ «جریانِ تغییر» (change feed) یا رویدادِ انتشار نیست؛ بازار، تبلیغات و API بیرونی فقط می‌توانند بپرسند.
5. نمای پیک برای مشتری (نام، تماسِ پوشیده، وضعیت، موقعیت) نیست.
6. رزروِ موجودی تصمیم‌نشده است (تعارضِ تصمیمِ ۱۴۰۵/۰۷/۲۷ با §۳۲.۲).
7. لوگو/تصویرِ دکان، برند/variant/بارکد در نمای عمومی، دستهٔ سراسریِ کالا نیست.
8. کمیسیون، سبدِ چنددکانی و پرداختِ آنلاین نیست (این‌ها برای مرحلهٔ ۳ِ §۴۰.۵ است، ولی جای فیلدش باید از حالا روشن باشد).
9. ستونِ آمادهٔ «آخرین تماسِ دستگاه» برای صفحه‌های پرترافیکِ بازار نیست.

## ۳. آنچه برنامهٔ مدیریت و سرور **از همین حالا** باید بسازند

ترتیب بر پایهٔ «اگر نسازیم، بعداً چه چیزی را باید دوباره بنویسیم». هر کار کوچک است و پشتِ پرچمِ خاموش می‌رود، مثلِ روالِ پروژه.

## ۴. بعداً: تبلیغات

بخشِ مستقل (§۴۰.۴)، فقط روی **نمای عمومی** سوار می‌شود و هیچ‌وقت به دادهٔ داخلیِ دکان دست نمی‌زند.

- **موجودیت‌ها**: `ad_campaigns` (صاحب: دکان / صاحبِ سامانه / تبلیغ‌دهندهٔ بیرونی)، `ad_creatives` (متن، عکس از همان خطِ عکس، هدف: `shop:<public_id>` / `product:<public_id>/<id>` / `url:<https…>`)، `ad_placements` (جای نمایش: بالای بازار، لای فهرست، صفحهٔ دکان…)، `ad_budgets`، `ad_events` (دیده‌شدن/کلیک، جمع‌شده در شمارنده‌های ساعتی، نه ردیفِ خامِ همیشگی).
- **قاعده‌ها**: برچسبِ روشنِ «تبلیغ» روی هر نمایش؛ تأیید پیش از انتشار (همان جریانِ `trust` برای ردِ محتوا)؛ زمان‌بندی با ساعتِ سرور؛ بودجه با کمِ اتمی و توقف در صفر؛ کالای تبلیغ‌شده باید در لحظهٔ نمایش «زنده» باشد (قاعدهٔ S1)؛ دکانِ معلق یا پنهان‌شده هیچ تبلیغی نمی‌گیرد.
- **ضدِ تقلب**: شمارشِ کلیک با محدودیتِ نرخ و حذفِ تکرار (دستگاه/IP/بازه)، بی ذخیرهٔ مکانِ مشتری.
- **پیش‌نیازها از همین قرارداد**: S2 (نمای عمومی)، S3 (شناسهٔ پایدار)، S6 (جریانِ تغییر برای توقفِ فوریِ تبلیغِ کالای ناموجود/پنهان)، M3 (لوگو و تصویر).

## ۵. بعداً: API برای سیستم‌های دیگر

- **در**: `/api/public/v1/*`، فقط‌خواندنی در آغاز، روی همان ماژولِ نمای عمومی (S2) — یعنی API و بازار هرگز دو قرارداد نمی‌شوند.
- **کلید**: پایهٔ امروز `managed_apps` (کلیدِ خام فقط یک بار، فقط HMAC ذخیره) است؛ لازم است: محدوده‌ها (`shops:read`، `products:read`، `orders:create`، `webhooks`)، فهرستِ دکان‌های مجاز برای هر کلید، محدودیتِ نرخِ جدا برای هر کلید، لغو و چرخش، لاگِ ممیزی.
- **وب‌هوک**: از روی S6، با امضای HMAC، زمان و nonce، تلاشِ دوباره با فاصلهٔ فزاینده، حذفِ تکرار با `seq`.
- **ثبتِ سفارش از بیرون**: فقط با همان `orders.create` و کلیدِ یکتایی، `channel = 'api:<appId>'` (S10)، و همان دروازه‌ها و قیمتِ سرور.
- **نسخه‌بندی**: `schemaVersion` ِ S2؛ تغییرِ شکستن فقط با `/v2`.
