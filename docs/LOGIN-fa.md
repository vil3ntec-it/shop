# ورود با کدِ شش‌رقمیِ ایمیلی — قرارداد، همان‌طور که پیاده شده

مرجع: پرامپتِ «ورودِ بی‌نقص» صاحبِ سامانه. این سند می‌گوید سرور **واقعاً**
چه می‌دهد، کجا از متنِ پرامپت فاصله گرفته‌ایم و چرا. برنامهٔ اندروید،
برنامهٔ کامپیوتر و نسخهٔ وب همه با همین نوشته می‌شوند.

---

## ۱. نقشه

```
برنامه ──POST /api/auth/{app}/request-code──▶ سرور ──▶ صفِ otp_outbox ──▶ Worker ──▶ ایمیلِ مشتری
   ▲                                            │
   │◀──۲۰۰ {request_id, resend_after}───────────┘        (کاربر منتظرِ ایمیل نمی‌ماند)
   │
   ├──POST /api/auth/{app}/verify {request_id, code}──▶ توکن‌ها + user + subscription
   ├──هر درخواست: Authorization: Bearer <access>          (یک ساعت)
   └──۴۰۱ ⇒ POST /api/auth/refresh ⇒ جفتِ تازه            (چرخشی، نود روز)
```

سه ستون، همان‌طور که پرامپت خواست:

- **اول سلامت**: برنامه پیش از هر کاری `GET /api/health` می‌زند (مهلتِ سه
  ثانیه) و اگر جواب نداد همان لحظه می‌گوید «سرور در دسترس نیست» — نه بعد
  از سی ثانیه انتظار.
- **ایمیل از صف**: درخواستِ کد فوراً ۲۰۰ می‌گیرد؛ ارسال در Worker با تلاشِ
  دوباره انجام می‌شود.
- **وضعیتِ تحویل قابلِ پرسیدن است**: `request-status` می‌گوید رفت یا نرفت و چرا.

---

## ۲. مسیرها

همه زیرِ `/api` و `/api/v1` هر دو در دسترس‌اند. `{app}` = `shop` یا `pump`.

| مسیر | کار |
|---|---|
| `GET /api/health` | سریع، بی دیتابیس: `{ok, service, email_worker, version, time}` |
| `GET /api/ready` | حالِ کاملِ دیتابیس (برای مدیر و پنلِ خانگی) |
| `POST /api/auth/{app}/request-code` | `{email}` ⇒ `{request_id, expires_in, resend_after, masked_email}` |
| `GET /api/auth/{app}/request-status?request_id=` | `{state, reason, sent_at, attempts, can_resend_in, expires_in}` |
| `POST /api/auth/{app}/verify` | `{request_id, code, device_name}` ⇒ توکن‌ها + `user` + `subscription` |
| `POST /api/auth/refresh` | `{refresh_token}` ⇒ جفتِ تازه (چرخشی) |
| `POST /api/auth/logout` | باطل کردنِ نشستِ همین دستگاه |
| `GET /api/me/heartbeat` | اشتراک، روزهای مانده، قابلیت‌ها، زمانِ سرور |
| `POST /api/errors` | گزارشِ خطای برنامه (توکن اختیاری) |

هدرهای هر درخواست: `X-App`، `X-Device`، `X-App-Version`، `X-Request-Id`.

`state` در `request-status` یکی از این‌هاست: `queued` · `sending` · `sent` ·
`failed` (با `reason`).

### کدهای خطا

| HTTP | `error` | رفتارِ برنامه |
|---|---|---|
| ۴۰۰ | `INVALID_EMAIL` · `CODE_WRONG` (با `attempts_left`) · `CODE_EXPIRED` · `REQUEST_NOT_FOUND` · `APP_UNKNOWN` | پیامِ `message` را نشان بده، همان صفحه بمان |
| ۴۰۱ | نشست منقضی | یک بار Refresh، بعد تکرارِ درخواست؛ باز ۴۰۱ ⇒ صفحهٔ ورود |
| ۴۲۳ | `LOCKED` (با `retry_after`) | شمارشِ معکوس، خانه‌ها غیرفعال |
| ۴۲۶ | `UPGRADE_REQUIRED` (فقط در Sync) | opها نگه داشته می‌شوند تا سرور به‌روز شود |
| ۴۲۹ | `RATE_LIMITED` (با `retry_after`) | دکمه غیرفعال با شمارشِ معکوس |
| ۵۰۳ | `EMAIL_SERVICE_DOWN` | پیام + تلاشِ دوبارهٔ خودکار ۵/۱۰/۲۰ ثانیه |

هر خطا `{ok:false, error, message}` است؛ `message` فارسیِ آدمیزاد و
`error` برای تصمیمِ برنامه. «هیچی نشد» وجود ندارد.

## ۳. قاعده‌ها

- کد ۶ رقمی، CSPRNG، **۵ دقیقه**، یک‌بارمصرف، و فقط **آخرین** کد معتبر است.
- **هیچ‌جا خام ذخیره یا لاگ نمی‌شود**: در دفتر `HMAC(app \n email \n code)`
  می‌نشیند، به‌علاوهٔ یک نسخهٔ رمزشده با AES-GCM که تنها مصرفش «نمایشِ کد
  به مدیر» است و با مصرف یا انقضا همان لحظه پاک می‌شود. مقایسه با زمانِ ثابت.
- کدِ یک برنامه در برنامهٔ دیگر بی‌معناست — `app` داخلِ خودِ هش است.
- سقف‌ها: **۲۰ درخواست/IP/۱۰ دقیقه**، **۵ کد/ایمیل/ساعت**، **۶۰ ثانیه** تا
  ارسالِ دوباره، **۵ کدِ اشتباه ⇒ ۱۵ دقیقه قفل**.
- پاسخِ `request-code` برای ایمیلِ ناموجود هم ۲۰۰ است (ضدِ شمارش).
- ثبت‌نام و ورود یکی‌اند: حسابِ نبوده هنگامِ `verify`ِ موفق ساخته می‌شود.
- ارقامِ فارسی و عربی همه‌جا به انگلیسی برمی‌گردند — در ایمیل و در کد.

## ۴. صف و Worker ایمیل

`otp_outbox` یک ردیف به ازای هر درخواست: `queued → sending → sent | failed`.

- تا **۴ تلاش** با عقب‌نشینیِ نمایی (۲، ۴، ۸ ثانیه).
- **مهلتِ سختِ ۸ ثانیه** برای هر ارسال (`AbortController`).
- **مدارشکن**: ۵ شکستِ پشتِ سرِ هم ⇒ باز؛ پس از ۳۰ ثانیه نیمه‌باز.
  `email_worker` در `/api/health` همین را می‌گوید.
- `Idempotency-Key` = همان `request_id`؛ یک ردیف دو بار فرستاده نمی‌شود.
- دلیلِ شکست دقیق است: `email_service_timeout` · `email_service_error` ·
  `invalid_recipient` · `expired`.
- **کدِ منقضی فرستاده نمی‌شود** — ایمیلِ کدِ مرده فقط گیج می‌کند.
- شکستِ نهایی، و «بیش از سه شکست در ده دقیقه»، به مدیر خبر می‌دهند.

عنوانِ ایمیل کد را در خودش دارد (`کد ورود دکان: ۴۸۳۹۲۰`) تا در پیش‌نمایشِ
گوشی دیده شود؛ بدنه RTL با نسخهٔ متنِ ساده در کنارش.

---

## ۵. توکن‌ها

- **دسترسی: یک ساعت. تازه‌سازی: نود روز و چرخشی** — هر تازه‌سازی جفتِ
  تازه می‌دهد و قبلی باطل می‌شود.
- **پنجرهٔ ارفاقِ ۳۰ ثانیه‌ای**: توکنِ تازه‌سازیِ باطل‌شده تا سی ثانیه هنوز
  پذیرفته می‌شود، پس دو درخواستِ موازی کسی را بیرون نمی‌اندازند.
  ⚠️ زنجیره **تا آخر** دنبال می‌شود (تا ۱۲ حلقه)، نه یک گام: کاربری که در
  همان سی ثانیه سه بار تلاش کند هم باید سالم بماند. این یک باگِ واقعی بود
  و سنجهٔ ۹ب قفلش کرده.
- توکنِ هر بخش در بخشِ دیگر **پیدا نمی‌شود**، نه «دسترسی نداری».
- توکنِ تازه‌سازی کلیدِ در نیست: روی مسیرهای معمولی ۴۰۱ می‌گیرد.

## ۶. میزِ «ورودها» در پنل

`/api/admin/logins` — برای وقتی مشتری زنگ می‌زند «کد نیامد»:

| مسیر | کار |
|---|---|
| `GET /api/admin/logins?email=&app=` | درخواست‌های اخیر: حال، دلیل، تلاش‌ها، IP، دستگاه |
| `GET /api/admin/logins/stats` | p50/p95ِ تحویل، درصدِ ناموفق، حالِ مدارشکن، هشدارها |
| `POST /api/admin/logins/:id/resend` | همان کد دوباره برود |
| `POST /api/admin/logins/:id/reveal` | **فقط مدیرِ کل**، با ثبت در دفترِ رخدادها |
| `POST /api/admin/logins/unlock` | برداشتنِ قفلِ ۱۵ دقیقه‌ای |

⛔ کد هیچ‌وقت در فهرست نمی‌آید — فقط در پاسخِ همان مسیرِ جدا، و فقط تا
وقتی زنده است.

## ۷. ایمیل نمی‌رسد — درختِ عیب‌یابی

| نشانه | علت | کار |
|---|---|---|
| `state=failed`, `reason=email_service_timeout` | سرویسِ ایمیل کند یا خاموش | SMTP را بسنجید؛ مدارشکن باز شده |
| `state=failed`, `reason=invalid_recipient` | ایمیلِ غلط | مشتری ایمیل را درست وارد کند |
| `state=sent` ولی مشتری نمی‌بیند | Spam یا تأخیرِ Gmail | پوشهٔ Spam؛ SPF/DKIM/DMARC؛ کد در عنوان هست |
| `state=queued` طولانی | Worker خاموش | `/api/health` ⇒ `email_worker: down` |
| «سرور در دسترس نیست» | اینترنت، نشانی، یا تونل | بررسیِ پله‌ایِ خودِ برنامه |
| کدِ درست ولی `CODE_WRONG` | ارقامِ فارسی، فاصله، یا کدِ قدیمی | فقط آخرین کد معتبر است |
| بعد از ورود بیرون می‌اندازد | تازه‌سازیِ موازی یا `X-App`ِ غلط | پنجرهٔ ارفاق و سنجشِ بخش |

## ۸. سه انحراف از متنِ پرامپت — با دلیل

| پرامپت | این‌جا | چرا |
|---|---|---|
| Redis برای کد و سقف‌ها | جدول‌های `login_requests` · `otp_outbox` · `login_locks` با ستونِ انقضا | کامپیوترِ خانگی ویندوز است و Redis ندارد؛ «یک سرور، یک دفتر». معناها عیناً همان‌اند و همه سنجیده شده‌اند |
| BullMQ برای صف | جدول + حلقهٔ Worker | همان تلاشِ دوباره، مهلت و مدارشکن، بی وابستگیِ تازه |
| JWT با EdDSA | همان توکنِ دفتریِ امروز | برنامه‌های نصب‌شده همین را دارند؛ عوض کردنش یعنی بیرون افتادنِ همهٔ مشتری‌های امروز. آن‌چه پرامپت واقعاً می‌خواست — چرخشی بودن، پنجرهٔ ارفاق، و سنجشِ `X-App` — اضافه شد |

⚠️ و یک چیزِ تنظیم‌پذیر که پرامپت ثابت گرفته بود: سقفِ IP با
`LOGIN_IP_MAX` عوض می‌شود. پشتِ تونل، تا وقتی `TRUST_PROXY=true` نباشد
همهٔ مشتری‌ها **یک** IP دیده می‌شوند و سقفِ بیستِ ثابت یعنی نفرِ
بیست‌ویکم بی آن‌که کاری کرده باشد قفل می‌شود.

## ۹. آزمون

```
npm run test:login        قراردادِ ورود (۱۷ سنجه) + Sync v1 (۱۶ سنجه)
npm test                  کلِ سرور روی PostgreSQL
npm run test:pglite       همان‌ها روی PGlite
```

ماتریسِ بخشِ ۸ پرامپت، بندهای ۱ تا ۱۵، همه سبز — روی هر دو راه‌انداز.

⚠️ **سه بندِ End-to-End سنجیده نشده‌اند و نباید ادعا شوند**: ایمیلِ واقعی
در Gmail زیرِ پنج ثانیه، همان از پشتِ تونل، و همان با اینترنتِ ضعیف. هر
سه به سرویسِ ایمیلِ واقعی و دامنهٔ واقعی نیاز دارند و باید روی کامپیوترِ
خودِ صاحبِ سامانه یک بار دویده شوند.
