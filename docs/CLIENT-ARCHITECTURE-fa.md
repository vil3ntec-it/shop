# معماری Client — اتصال به Backend مرکزی

این سند فقط دربارهٔ **برنامه‌های مشتری** است: نسخهٔ وب (`index.html` و
`license/`) و برنامهٔ فروشگاه (`android-native/`). برنامهٔ مدیریت
(`admin-android/`) جداست و اینجا موضوع بحث نیست.

---

## قاعدهٔ اصلی

> برنامه یک **دامنه** می‌شناسد، نه یک **سرور**.

هیچ نشانیِ IP جایی در کدِ Client نوشته نمی‌شود. اگر Backend فردا از
رایانهٔ خانه به یک VPS برود، تا وقتی همان دامنه به جای تازه اشاره کند،
هیچ‌کدام از برنامه‌ها نمی‌فهمند چیزی عوض شده و نسخهٔ تازه‌ای لازم نیست.

این قاعده در کد هم اجرا می‌شود، نه فقط در حرف:
`ApiConfig.reject()` نشانیِ عددی را در نسخهٔ منتشرشده رد می‌کند.

---

## لایه‌ها

```
        صفحه‌ها (Compose / HTML)
                 ↓            ← فقط مخزن را صدا می‌زند
        مخزن‌ها (data/repo)
                 ↓            ← منطقِ کار، مدل‌های نوع‌دار
        ApiClient (core/net)
                 ↓            ← توکن، تازه‌سازی نشست، ۴۰۱
        HttpEngine (core/net)
                 ↓            ← مهلت، تلاش دوباره، دسته‌بندی خطا
               HTTPS
                 ↓
      https://api.YOURDOMAIN.com
```

هیچ صفحه‌ای کارگزارِ شبکه نمی‌سازد، نشانیِ سرور را نمی‌خواند، و توکن را
دست نمی‌زند. صفحه فقط `Backend.shop(context)` را می‌گیرد و کارش را
می‌کند.

| لایه | فایل | کارش |
|---|---|---|
| پیکربندی | `core/config/ApiConfig.kt` | قاعده‌های نشانی — خالص، بی‌اندروید، سنجیدنی |
| پیکربندی | `core/config/AppConfig.kt` | نشانیِ واقعی، از `BuildConfig` یا حافظهٔ دستگاه |
| مسیرها | `core/net/ApiEndpoints.kt` | همهٔ مسیرها؛ نسخه یک بار، نه بیست‌وچند بار |
| خطا | `core/net/ApiFailure.kt` | دسته‌بندیِ خطا با پیامِ فارسی |
| حمل | `core/net/HttpEngine.kt` | HTTP خام، مهلت، تلاش دوباره |
| نشست | `core/net/ApiClient.kt` | توکن، و «۴۰۱ → تازه‌سازی → تکرار» |
| توکن | `core/net/TokenStore.kt` | نگهداریِ رمزشده در Keystore گوشی |
| مدل | `core/model/ApiModels.kt` | شکلِ هر درخواست و پاسخ |
| مخزن | `data/repo/*Repository.kt` | آنچه صفحه‌ها صدا می‌زنند |
| اتصال | `data/repo/Backend.kt` | تنها جایی که لایه‌ها به هم بسته می‌شوند |

نسخهٔ وب همین قاعده را دارد، ساده‌تر: `license/api-config.js` تنها جایی
است که نشانی از آن خوانده می‌شود، و `license-client.js` و `shop-sync.js`
و `vip.js` و `index.html` همان را صدا می‌زنند.

## تنظیمِ نشانی

نشانی **در سورس نیست**؛ از پیکربندی می‌آید.

### برنامهٔ اندروید

هنگامِ ساخت، از متغیرِ محیطی:

```
TOHID_API_BASE=https://api.YOURDOMAIN.com
```

در GitHub Actions این یک `vars` است نه `secrets` — چون این نشانی راز
نیست: هر کسی که برنامه را باز کند با همین دامنه حرف می‌زند و از روی
ترافیک دیده می‌شود. راز، چیزهایی است که فقط روی سرور می‌مانند: رمزِ
دیتابیس، کلیدِ پیامک، توکنِ واتساپ.

اگر تنظیم نشده باشد، نسخه به هیچ سروری بسته نمی‌شود و برنامه کاملاً
آفلاین کار می‌کند — نه خطایی، نه قابلیتی که قفل شود.

### نسخهٔ وب

یک خط در `<head>` فایلِ `index.html`:

```html
<meta name="tohid-api-base" content="https://api.YOURDOMAIN.com">
```

خالی گذاشتنش هم مثل بالا: آفلاین، بدونِ قفل.

### سرورِ شخصی

اگر نسخه بدونِ نشانی ساخته شده باشد، کادرِ نشانی در برنامه پیدا می‌شود و
کاربر خودش می‌زند. در نسخه‌ای که به دامنهٔ مرکزی بسته شده، آن کادر اصلاً
نشان داده نمی‌شود و نوشتن روی نشانی بی‌اثر است — یعنی کسی نمی‌تواند
برنامه را به سرورِ خودش ببرد.

## نسخهٔ API

`/api/v1` — یک بار در `ApiConfig.API_VERSION` (و `TohidApiConfig.VERSION`
در وب). مسیرها بدونِ پیشوند نوشته می‌شوند (`/auth/login`) و پیشوند
همان‌جا یک بار چسبانده می‌شود. رفتن به `v2` یک تغییرِ یک‌خطی است.

نشانی‌ای که کاربر با `/api/v1` چسبیده بزند — چون همان را در مرورگر دیده —
خودکار مرتب می‌شود، وگرنه مسیرها `/api/v1/api/v1/…` می‌شدند.

## نشست

توکنِ دسترسی روی سرور **یک ساعت** عمر دارد؛ توکنِ تازه‌سازی نود روز.

هر `401` روی یک درخواستِ توکن‌دار یعنی «توکن پیر شده»: یک بار تازه‌اش
می‌کنیم و همان درخواست را دوباره می‌فرستیم. کاربر هیچ‌کدام را نمی‌بیند.
فقط اگر تازه‌سازی هم نگرفت، «دوباره وارد شوید».

تازه‌سازی پشتِ یک قفلِ مشترک است: اگر همگام‌سازی و صفحهٔ اشتراک با هم به
`401` بخورند، یکی تازه می‌کند و آن یکی منتظرِ همان می‌ماند.

قطعیِ گذرا (نت نیست، سرور ۵۰۳) نشست را پاک **نمی‌کند** — وگرنه کسی که در
مسیرِ بی‌آنتن است بی‌دلیل از حسابش بیرون می‌افتاد.

توکن‌ها با کلیدی در Keystore خودِ گوشی رمز می‌شوند و هیچ‌وقت log
نمی‌شوند.

## خطاها

هر خطا دسته و پیامِ فارسیِ خودش را دارد:

| حالت | پیام |
|---|---|
| `Offline` | اینترنت وصل نیست |
| `Unreachable` | سرور در دسترس نیست |
| `Timeout` | سرور به‌موقع پاسخ نداد |
| `SessionExpired` | نشست شما تمام شد؛ دوباره وارد شوید |
| `Unauthorized` | پیامِ خودِ سرور |
| `Forbidden` | پیامِ خودِ سرور (مثلاً «اشتراک شما این را ندارد») |
| `ServerFault` | سرور خطا داد؛ کمی بعد دوباره امتحان کنید |
| `InvalidResponse` | پاسخ سرور خوانده نشد |

پیامِ خودِ سرور همیشه مقدم است — سرور می‌داند «۹۰ ثانیه دیگر می‌توانید کد
تازه بخواهید»، ما فقط می‌دانیم «۴۲۹».

## تلاشِ دوباره

فقط برای درخواست‌هایی که تکرارشان بی‌خطر است (خواندن) و فقط برای خطاهایی
که ممکن است گذرا باشند. حداکثر دو بار، با فاصلهٔ دوبرابرشونده.

**فرستادنِ فروش هیچ‌وقت دوباره فرستاده نمی‌شود.** دو بار ثبت شدنِ یک
فاکتور از یک بار نرسیدنش بدتر است.

---

## قابلیتِ تازه

اگر قابلیتی لازم است که API فعلی ندارد، راه‌حلِ موقت داخلِ Client ساخته
نمی‌شود. اول مسیرِ API مشخص می‌شود، بعد یک خط به `ApiEndpoints` اضافه
می‌شود، بعد Client مطابقِ همان قرار نوشته می‌شود.

منطقِ کاری که باید بینِ وب و اندروید و هر Client دیگری مشترک باشد، تا حدِ
ممکن روی Backend می‌ماند — نه دو بار نوشته شود و کم‌کم از هم فاصله
بگیرد.

واقعیِ HTTP.
